How Hooks Remember Things Between Renders

This is a detour before returning to Lesson 2 — that lesson assumed you already knew how any hook "remembers" something across renders. This lesson fills that gap. Once it clicks, Lesson 2 should make a lot more sense on a re-read.

You've already lived this problem once

Remember building PlayAudioButton: you tried a plain const isPlaying = false, and we established two things — a const can't be reassigned at all, and even a mutable let wouldn't make the icon change, because changing a plain variable doesn't tell React to redraw anything. You fixed it with useState.

Here's the piece that was missing then: how does useState remember isPlaying's value from one render to the next, when the entire component function — including every const inside it — runs again from scratch on every render?

React's answer: a private, ordered list per component

Each component instance gets its own hidden list of storage slots that survives across that instance's re-renders — think of it as an array React keeps privately, one entry per hook call. When your component function runs again, its local consts and lets are all thrown away and recreated — but that hidden list is not. React hands your hooks back into the same slots they used last time.

Primary source: react.dev — State: A Component's Memory 
function PlayAudioButton({ audioFile }) {
  const player = useWordAudio(audioFile);      // slot 0
  const [isPlaying, setIsPlaying] = useState(false); // slot 1
  ...
}

Every time PlayAudioButton renders, useState(false) runs again — but React doesn't hand back a fresh false every time. It looks up slot 1, sees a value already stored there from last render (say, true, because you tapped the button), and hands that back instead of the false you wrote in the code. That's the whole trick.

Why hook order can never change: React identifies "which slot is this" purely by the order hooks are called in, not by variable name. If you wrapped a hook call in an if, some renders would call it and others wouldn't — shifting every subsequent hook into the wrong slot. That's the real reason hooks can't be conditional.

Now apply this to useCallback

useCallback uses the exact same slot mechanism — its slot stores two things: the function from last render, and the dependency array from last render. Each render, it compares the new dependency array against the stored one, item by item. Unchanged? Hand back the old stored function, let the freshly-written one (which you just saw gets recreated every render, from Lesson 2) get thrown away unused. Changed? Store and return the new one instead.

That's the mechanism behind the "stable reference" idea from Lesson 2 — it's not magic, it's the same memory-slot system useState uses, just storing a function instead of a value.
